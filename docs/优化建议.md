# ChenDoc 项目优化建议

本文基于 `FILE_GUIDE.md` 和当前项目代码结构整理，重点是项目本身的代码质量、稳定性、权限边界、测试覆盖、运维可靠性和后续可维护性。

## 保护区

以下两块先不要动业务逻辑：

| 模块 | 注意 |
| --- | --- |
| R2 上传 | 不建议改 `server/src/modules/uploads/*` 的预签名、上传完成校验、对象路径、Content-Type/Content-Length 校验、CORS 自动处理逻辑。当前上传链路已经做了比较完整的防篡改和 R2 实体验证，改动风险高。 |
| 公开分享 | 不建议改 `server/src/modules/shares/*`、`server/src/modules/public/*` 的启用、过期、密码 token、删除文档不可访问等访问边界。公开分享是外部访问入口，任何小改都可能造成内容误公开或访问失效。 |

如果以后确实必须动这两块，先补完整回归测试，再改代码。

## 星级排序

| 星级 | 优先级 | 优化项 | 主要落点 |
| --- | --- | --- | --- |
| ★★★★★ | 最需要改 | 扩大测试覆盖 | `server/src/modules/docs/*`、`settings/*`、`auth/*`、`db/migrate.ts` |
| ★★★★★ | 最需要改 | 明确普通用户和管理员权限模型 | `server/src/modules/docs/docs.routes.ts`、`apps/admin/src/router/index.ts`、`stores/auth.ts` |
| ★★★★☆ | 高优先级 | 强化数据库迁移和发布前备份流程 | `server/src/db/migrate.ts`、`scripts/backup-sqlite.js`、`scripts/preflight-deploy.js` |
| ★★★★☆ | 高优先级 | 补齐操作日志覆盖 | `operation_logs`、文档删除、设置变更、邀请码、管理员动作 |
| ★★★★☆ | 高优先级 | 处理文档版本无限增长问题 | `server/src/modules/docs/docs.service.ts`、`doc_versions` |
| ★★★☆☆ | 中优先级 | 前端状态和错误处理统一 | `apps/admin/src/api/request.ts`、`stores/*`、页面组件 |
| ★★★☆☆ | 中优先级 | 文档编辑保存体验优化 | `DocEditorPage.vue`、`ChendocEditor.vue`、`stores/doc.ts` |
| ★★★☆☆ | 中优先级 | 搜索性能和结果体验优化 | `docs.service.ts`、`docs` 表索引、后续 FTS5 |
| ★★☆☆☆ | 可排期 | 清理运行产物和项目边界 | `.gitignore`、`dist/`、`data/`、`release/`、`node_modules/` |
| ★★☆☆☆ | 可排期 | 前端样式和组件复用整理 | `components/common/*`、各页面 CSS |

## ★★★★★ 1. 扩大测试覆盖

这是当前最需要改的地方。现在测试主要集中在公开分享访问边界，其他核心功能几乎没有自动化保护。项目已经有登录、文档、回收站、危险删除、设置、邀请码、数据库迁移等高风险逻辑，但改动时缺少安全网。

建议优先补：

| 模块 | 必测场景 |
| --- | --- |
| 文档 | 创建、更新、软删、恢复、硬删、版本生成、版本恢复、非管理员访问。 |
| 设置 | R2 密钥保存脱敏、空密钥保留旧值、站点配置保存、非法 URL 拒绝。 |
| 鉴权 | 无 session、无效 session、禁用用户、普通用户访问 admin 接口。 |
| 邀请码 | 创建、使用、过期、重复使用、禁用。 |
| 数据迁移 | 空库迁移成功、重复执行迁移成功、旧表补字段成功。 |

先补这些测试，比继续加功能更划算。后面任何重构都能跑一遍，心里踏实很多。

## ★★★★★ 2. 明确权限模型

当前代码里存在“系统有 user/admin 两种角色，但大部分后台能力只给 admin”的状态：

| 现状 | 风险 |
| --- | --- |
| 路由里 `/admin` 需要登录，但子页面多数需要 admin。 | 普通用户登录后能进后台壳，但实际可用能力有限。 |
| `/api/docs` 只要求登录，但 `listDocs` 对非 admin 返回空数组。 | 权限结果不直观，前端和后端语义不完全一致。 |
| 注册用户默认是 `user`。 | 如果普通用户没有明确用途，后续容易误以为他们能管理自己的文档。 |

建议二选一：

1. 如果 ChenDoc 只做单管理员私有文档系统：收紧路由和 API，明确普通用户只用于预留或禁止进入后台。
2. 如果要支持多用户文档：补 owner/space 权限，文档列表、详情、编辑、删除都按用户和空间隔离。

这里建议先走第一条，成本低，也符合当前项目“轻量私有文档系统”的定位。

## ★★★★☆ 3. 强化数据库迁移和备份

当前 `migrate.ts` 使用 `CREATE TABLE IF NOT EXISTS` 加 `ALTER TABLE ADD COLUMN`，轻量可用，但后续字段一多，容易出现线上库结构和源码 schema 不一致。

建议：

| 建议 | 说明 |
| --- | --- |
| 给迁移加版本记录 | 增加一张简单的 `schema_migrations` 表，记录已执行迁移。 |
| 发布前强制备份 | 发布流程里先跑 `npm run db:backup`，再跑迁移和部署检查。 |
| 迁移保持幂等 | 每条迁移重复执行不能报错。 |
| 迁移前后 smoke test | 用临时 SQLite 库跑一次初始化迁移和重复迁移。 |

这块优先级很高，因为 SQLite 单机部署一旦迁移出问题，恢复成本会比改页面高很多。

## ★★★★☆ 4. 补齐操作日志覆盖

项目已经有 `operation_logs` 表，但目前主要在危险删除里使用。建议把它变成真正的审计能力。

优先记录：

| 动作 | 价值 |
| --- | --- |
| 文档硬删、恢复、危险删除 | 出问题时能查是谁删的。 |
| 设置变更 | 尤其站点配置、存储配置、密钥相关配置。 |
| 邀请码创建、禁用、删除 | 注册入口需要可追溯。 |
| 管理员改密码、初始化、重置 | 安全排查必备。 |
| 登录失败过多 | 后续可用于风控和封禁策略。 |

R2 上传和公开分享逻辑先不要改。这里可以只在外围动作补日志，不改上传/分享核心判断。

## ★★★★☆ 5. 控制文档版本增长

`updateDoc` 每次标题或内容变化都会插入 `doc_versions`。如果编辑器频繁保存，版本表会增长很快。

建议：

| 建议 | 说明 |
| --- | --- |
| 增加版本生成节流 | 比如同一文档 2 分钟内多次保存只保留一个版本。 |
| 增加版本上限 | 每篇文档保留最近 50 或 100 个版本。 |
| 增加版本差异判断 | 内容完全相同不生成新版本。 |
| 提供清理脚本 | 定期清理过旧版本。 |

这是比较实在的稳定性优化，不影响现有功能，但能防止数据库慢慢膨胀。

## ★★★☆☆ 6. 统一前端状态和错误处理

当前 `request.ts` 已经有统一请求封装，但页面层的 loading、错误提示、空状态、重试逻辑还可以更一致。

建议：

| 建议 | 落点 |
| --- | --- |
| 统一 API 错误提示 | `ApiError` 里保留 status 和 message，页面统一展示。 |
| 统一加载状态 | 列表、详情、保存、删除用一致的 loading 命名和禁用策略。 |
| 统一登录过期处理 | 401 时自动清 session 并跳回登录页。 |
| store 缓存失效策略 | `detailCache` 现在没有过期机制，后续多人或多窗口使用容易看到旧数据。 |

这块不会马上炸，但会明显影响维护体验和用户操作稳定性。

## ★★★☆☆ 7. 优化文档编辑保存体验

编辑器是 ChenDoc 的核心体验。当前建议先优化外围体验，不碰 R2 上传链路。

可做：

| 建议 | 说明 |
| --- | --- |
| 保存状态更明确 | 显示未保存、保存中、已保存、保存失败。 |
| 自动保存防抖 | 避免每次输入都触发版本写入。 |
| 离开页面提醒 | 有未保存内容时提示。 |
| 保存失败可重试 | 网络失败时保留本地内容，不直接丢状态。 |
| 大文档性能检查 | 大 HTML、大 JSON 内容编辑时关注卡顿和保存耗时。 |

这项排在中优先级，因为它直接影响日常使用，但最好在版本增长控制之后做。

## ★★★☆☆ 8. 搜索性能和结果体验

当前搜索使用 `LIKE` 扫标题、摘要、HTML、分享码和 slug。轻量使用没问题，文档数量上来以后会变慢。

建议分阶段：

| 阶段 | 做法 |
| --- | --- |
| 现在 | 给搜索逻辑补测试，确认 deleted 文档不会出现在结果里。 |
| 中期 | 给常用过滤字段加索引，例如 `updated_at`、`space_id`、`pinned`。 |
| 后期 | 引入 SQLite FTS5，标题、摘要、正文纯文本建全文索引。 |
| 前端 | 搜索结果显示命中摘要，别只显示标题。 |

这块不急于马上改，但文档量增长后会变成明显瓶颈。

## ★★☆☆☆ 9. 清理运行产物和项目边界

`.gitignore` 已经覆盖了 `node_modules/`、`dist/`、`server/dist/`、`server/public/admin/`、`data/`、`.env`、日志等，这个方向主要是保持纪律。

建议：

| 建议 | 说明 |
| --- | --- |
| 日常搜索排除生成目录 | 避免在 `dist`、`node_modules`、`data` 里浪费时间。 |
| 不手改构建产物 | 改源码后重新 build。 |
| release 包和运行库分离 | 防止部署包、数据库、日志混在源码判断里。 |
| 本地工具目录不纳入项目判断 | `../.tools/` 只当本机工具，不当业务代码。 |

这不是最紧急的问题，但会影响长期维护效率。

## ★★☆☆☆ 10. 前端样式和组件复用整理

现在页面和 CSS 拆得比较直观，但后续功能增加后，弹窗、空状态、确认操作、表单校验、按钮状态可以继续抽通用层。

建议：

| 建议 | 说明 |
| --- | --- |
| 表单错误展示统一 | 登录、注册、设置、邀请码、删除页用同一套错误样式。 |
| ConfirmDialog 能力增强 | 支持危险等级、二次确认文字、loading。 |
| EmptyState 统一使用 | 文档列表、回收站、邀请码、设置测试失败等场景统一。 |
| 页面 CSS 收敛变量 | 常用 spacing、色值、边框、阴影尽量走全局变量。 |

这项可以穿插做，不建议排在核心稳定性前面。

## 最推荐先改的 5 件事

1. 补 `docs.service.ts` 的文档 CRUD 和版本测试。
2. 明确普通用户到底能不能用后台；如果不能，就前后端一起收紧。
3. 给迁移增加 smoke test，并把发布前备份变成固定流程。
4. 扩展 `operation_logs`，先覆盖文档删除、设置变更、邀请码管理。
5. 给文档版本增加节流、去重或数量上限，防止数据库越用越胖。

## 暂时不要改的事

1. 不改 R2 上传核心逻辑。
2. 不改公开分享访问判断。
3. 不为了“看起来更规范”重构全项目目录。
4. 不先做大规模 UI 重写。
5. 不在没有测试的情况下调整鉴权和数据迁移。
